Problema și soluția

De ce avem nevoie de control al versiunilor?

Când mai multe persoane lucrează la aceleași fișiere apar versiuni suprapuse, modificări pierdute și întrebarea „cine a schimbat asta?”. Git și GitHub rezolvă aceste probleme.

🧩

Git

Sistem de control al versiunilor distribuit. Fiecare membru are pe calculator o copie completă a proiectului și a istoricului. Funcționează și fără internet.

☁️

GitHub

Platformă online care găzduiește repository-uri Git și adaugă instrumente de colaborare: Pull Requests, Issues, Teams, Actions și GitHub Pages.

🤝

Împreună

Git gestionează versiunile local, GitHub sincronizează echipa. Rezultat: lucru în paralel, revizuire de cod și un istoric transparent.

Repository

Dosarul proiectului împreună cu întreg istoricul.

Commit

Un „instantaneu” salvat, cu mesaj descriptiv.

Branch

Linie separată de dezvoltare, fără risc pentru versiunea principală.

Pull Request

Propunere de includere a modificărilor, cu revizuire de colegi.

Interactiv

Simulator de ramuri (branch) și merge

Apasă butoanele și vezi cum se construiește istoricul unui proiect. Jos apare comanda Git echivalentă.

Cum lucrează o echipă

Fluxul de lucru pas cu pas

Acesta este fluxul folosit în aproape orice echipă de dezvoltare.

Crearea repository-ului

Proprietarul creează proiectul pe GitHub și își invită colegii ca collaborators.

Clonarea

Fiecare coleg rulează git clone și primește proiectul cu tot istoricul.

Ramură nouă pentru fiecare sarcină

git checkout -b functie-noua – munca se izolează de versiunea stabilă.

Salvarea modificărilor

git add și git commit -m "mesaj" – pași mici, cu mesaje clare.

Trimiterea pe GitHub

git push și deschiderea unui Pull Request.

Revizuirea codului

Colegii comentează, cer corecturi și aprobă modificările.

Merge în main

După aprobare, ramura este unită cu versiunea principală.

Sincronizarea echipei

Toți rulează git pull și lucrează mai departe pe versiunea actualizată.

Git Bash

Comenzile necesare, gata de copiat

Înlocuiește NUME-UTILIZATOR cu username-ul tău de GitHub.

# o singură dată pe calculatorgit config --global user.name "Numele Prenumele" git config --global user.email "email@exemplu.com" git config --list
# creare dosar și repository localmkdir studiu-de-caz cd studiu-de-caz git init
# salvarea primului commitgit status git add index.html git commit -m "Adaug pagina index.html"
# după ce ai creat repository-ul gol pe github.comgit branch -M main git remote add origin https://github.com/NUME-UTILIZATOR/studiu-de-caz.git git push -u origin main
# hostare: Settings → Pages → Deploy from a branch → main → / (root)https://NUME-UTILIZATOR.github.io/studiu-de-caz/
# coleg nou: clonează proiectulgit clone https://github.com/NUME-UTILIZATOR/studiu-de-caz.git cd studiu-de-caz
# flux zilnicgit pull git checkout -b ramura-mea git add . git commit -m "Descriere clară a modificării" git push -u origin ramura-mea
# istoric și diferențegit log --oneline --graph git diff git blame index.html
Cu și fără

Același proiect: fără Git vs. cu Git

Situație Fără Git / GitHub Cu Git / GitHub
Doi colegi modifică același fișier Un fișier îl suprascrie pe celălalt Modificările se unesc sau se semnalează conflictul
O modificare a stricat proiectul Căutare manuală a unei copii vechi git revert – revenire instantanee
Un membru nou intră în echipă Primește o arhivă pe e-mail git clone – are tot, cu istoric
Cine a scris o linie anume? Necunoscut git blame
Copie de siguranță Depinde de un singur calculator Proiectul există pe GitHub și la fiecare membru
Publicarea site-ului Server propriu, încărcare manuală GitHub Pages, gratuit

✔ Avantaje

  • Istoric complet al modificărilor
  • Lucru în paralel pe ramuri
  • Revizuirea codului prin Pull Request
  • Organizare prin Issues și Projects
  • Portofoliu public pentru dezvoltatori

✘ Limitări

  • Curbă de învățare la început
  • Conflicte de merge când se modifică aceleași rânduri
  • Fișierele binare mari se gestionează greu
